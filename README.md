A dual-pipeline image filtering project that applies Instagram-style effects on both CPU and GPU. The repository provides a sequential C++17 implementation and an accelerated CUDA implementation of the same filters, exposed through a consistent command-line interface and backed by automated tests, logging, and a configurable CMake build system.

The project is designed as a compact but well-structured image processing application. It loads images from a directory, applies a selected filter, and writes the transformed outputs to disk. The codebase is organized into clear modules for parsing, file I/O, logging, CPU filters, GPU kernels, and tests. This makes it useful both as a practical tool and as a reference project for learning how to move from scalar CPU loops to massively parallel CUDA execution.

## Project Overview

This repository implements three classic image effects:

- **Grayscale**
- **Sepia**
- **Brightness adjustment**

Each filter is available through:

1. a **CPU pipeline**, implemented with standard C++ loops over image buffers
2. a **GPU pipeline**, implemented with CUDA kernels and NVIDIA NPP primitives

The project emphasizes functional equivalence between both paths. A pixel processed on the CPU should follow the same mathematical rules as a pixel processed on the GPU. This is reflected in the test suite, which validates image loading, filter behavior, dimension preservation, clamping rules, and GPU execution when CUDA is enabled.

From a software engineering point of view, the repository demonstrates several important ideas:

- modular organization of image processing logic
- configurable build features through CMake options
- optional GPU acceleration without breaking CPU-only builds
- isolated CUDA translation units for host/device separation
- practical command-line usage for batch processing
- test-driven validation of image and filter behavior

## How the Filters Work

The project operates on RGB images stored as a flat 1D byte array:

```text
[R, G, B, R, G, B, R, G, B, ...]
```

Each pixel in the imags can indeed be though as a triplet of three bytes (`R`, `G`, and `B`), each represented as an unsigned 8-bit integer in the range `[0, 255]`. The project does not currently support alpha channels, so the channel count is fixed at `C = 3`.
For an image of width `W`, height `H`, and `C = 3` channels, the total number of bytes is:

```text
W × H × C
```

Each implemented filter transforms the source image into a new output image of the same dimensions.

### Grayscale

The grayscale conversion uses the standard luminosity method, which weights the three color channels according to human visual perception. Green contributes the most, followed by red, then blue.

For each pixel with channels `(R, G, B)`, the grayscale intensity `Y` is computed as:

$$
Y = 0.299R + 0.587G + 0.114B
$$

Because the project preserves a 3-channel RGB layout even after grayscale conversion, the output pixel becomes:

$$
(R', G', B') = (Y, Y, Y)
$$

#### CPU implementation

The CPU version:

1. allocates a new output buffer
2. iterates pixel by pixel
3. reads the input pixel's `R`, `G`, and `B`
4. computes `Y`
5. writes `Y` into all three output channels

This is implemented in `include/filters.h` inside `grayscale_filter()`.

#### GPU implementation

The CUDA grayscale kernel in `src/filters/grayscale.cu` uses one thread per byte, not one thread per pixel. For a byte index `idx`, it derives the owning pixel as:

$$
\text{pixel\_idx} = \left\lfloor \frac{idx}{channels} \right\rfloor
$$

Each thread:

1. reads the same source pixel's `R`, `G`, and `B`
2. computes `Y`
3. writes `Y` into its assigned output byte

This means three adjacent threads compute the same grayscale value for the same pixel and write it into the red, green, and blue output locations. The approach is not the most compute-efficient possible, but it is simple, correct, and easy to reason about.

### Sepia

The sepia effect applies a fixed linear color transform that produces a warmer, brownish tonal range. For each pixel `(R, G, B)`, the transformed output is:

$$
R' = 0.393R + 0.769G + 0.189B
$$

$$
G' = 0.349R + 0.686G + 0.168B
$$

$$
B' = 0.272R + 0.534G + 0.131B
$$

The results are then clamped to the valid 8-bit range:

$$
x' = \min(255, \max(0, x'))
$$

So the complete operation is:

$$
R' = \text{clamp}(0.393R + 0.769G + 0.189B, 0, 255)
$$

$$
G' = \text{clamp}(0.349R + 0.686G + 0.168B, 0, 255)
$$

$$
B' = \text{clamp}(0.272R + 0.534G + 0.131B, 0, 255)
$$

#### CPU implementation

The CPU version in `sepia_filter()` computes the three transformed channels for every pixel, clamps them, and stores them into a new image buffer.

#### GPU implementation

The CUDA sepia kernel in `src/filters/sepia.cu` follows a similar byte-oriented thread mapping as the grayscale kernel:

- one thread per output byte
- shared source pixel inferred via integer division
- output channel selected via:

$$
\text{channel} = idx \bmod channels
$$

Each thread computes the full sepia triplet `(R', G', B')` and then writes only the channel corresponding to `idx % channels`.

This design intentionally repeats some computation across neighboring threads. That is a valid engineering trade when prioritizing simplicity and correctness over aggressive micro-optimization. The code also includes comments discussing an alternative shared-memory approach and why it may not be faster in practice due to synchronization overhead.

### Brightness

Brightness adjustment adds a scalar offset `Δ` to every channel of every pixel:

$$
R' = \text{clamp}(R + \Delta, 0, 255)
$$

$$
G' = \text{clamp}(G + \Delta, 0, 255)
$$

$$
B' = \text{clamp}(B + \Delta, 0, 255)
$$

The project first clamps the requested delta itself to a safe range:

$$
\Delta \in [-255, 255]
$$

This ensures predictable behavior even if the user requests a very large positive or negative adjustment.

#### CPU implementation

The CPU brightness filter in `brightness_filter()`:

1. clamps the user-provided delta to `[-255, 255]`
2. iterates over every byte in the image
3. adds the delta
4. clamps the result to `[0, 255]`
5. stores the result in the output buffer

This implementation is channel-agnostic and therefore applies equally to all RGB bytes.

#### GPU implementation

The GPU brightness path is implemented differently from grayscale and sepia. Instead of a custom CUDA kernel, it delegates the arithmetic to **NVIDIA Performance Primitives (NPP)** in `src/filters/brightness.cu`.

The procedure is:

1. copy the input image from `d_input` to `d_output` on device memory
2. define the ROI as the entire image
3. choose the NPP primitive based on the sign of `Δ`
   - `nppiAddC_8u_C3IRSfs` for positive deltas
   - `nppiSubC_8u_C3IRSfs` for negative deltas
4. rely on NPP's saturating arithmetic to clamp values to `[0, 255]`

This is a good fit for brightness because it is a dense, element-wise transform that maps directly to highly optimized NPP routines.

## CUDA Implementation Details

The CUDA backend is organized around a `GpuImage` structure defined in `include/filters.h`:

- `d_input`
- `d_output`
- `bytes`
- `width`
- `height`
- `channels`

### Device memory lifecycle

The device execution flow is:

1. **Upload**
   - `gpu_upload()` allocates device buffers with `cudaMalloc`
   - host pixels are copied to `d_input` with `cudaMemcpy`

2. **Execute**
   - `apply_gpu_filter()` selects the proper kernel or NPP operation
   - grayscale and sepia launch CUDA kernels
   - brightness calls the NPP wrapper

3. **Synchronize**
   - explicit synchronization is used after execution
   - kernel errors are checked through `CUDA_CHECK(...)`

4. **Download**
   - `gpu_download()` allocates host memory with `malloc`
   - result pixels are copied from `d_output` back to host memory

5. **Free**
   - `gpu_free()` releases both device buffers

### Kernel launch configuration

For the custom CUDA kernels, the launcher computes:

```text
threads_per_block = 256
blocks = ceil(total_bytes / threads_per_block)
```

Where `total_bytes = width × height × channels`.

This is a simple, reliable launch strategy for linear memory traversal.

### Why the CUDA code is split across `.cu` files

CUDA-specific syntax such as kernel launches:

```cpp
kernel<<<blocks, threads>>>(...)
```

cannot be compiled by a plain C++ compiler. For that reason, host/device CUDA code is isolated inside `.cu` translation units such as:

- `src/filters/filters.cu`
- `src/filters/grayscale.cu`
- `src/filters/sepia.cu`
- `src/filters/brightness.cu`

The project also enables:

```cmake
CUDA_SEPARABLE_COMPILATION ON
```

which is required for multi-file CUDA device code linkage.

### CUDA architecture handling

When CUDA support is enabled, the project uses:

```cmake
set(CMAKE_CUDA_ARCHITECTURES native)
```

This asks CMake to detect the target GPU architecture automatically. It is convenient for local development and HPC environments where the available hardware may change.

### Performance perspective

From an algorithmic point of view, both the CPU and GPU versions still perform work proportional to the number of pixels. The difference is in execution model:

- the CPU handles work through ordinary sequential loops
- the GPU exposes far more parallel throughput for per-pixel operations

In practice, the GPU path is especially attractive for:

- large images
- large batches of images
- repeated filtering workloads

At the same time, end-to-end performance is also affected by:

- host-to-device memory transfer
- device-to-host memory transfer
- disk I/O
- image decode/encode time

For many real workloads, these costs dominate once the arithmetic itself becomes very fast.

## Automated Installation Script

The repository includes `scripts/install.sh`, which:

1. checks that it is being run from the project root
2. downloads STB headers if they are missing
3. downloads `spdlog` if it is missing
4. creates a `build/` directory
5. runs CMake
6. compiles the project

Usage:

```bash
(sudo) chmod +x scripts/install.sh
./scripts/install.sh
```

### What the script builds

By default, the project currently declares:

- `ENABLE_LOGGING=ON`
- `ENABLE_TESTS=OFF`
- `ENABLE_DEBUG=OFF`
- `ENABLE_CUDA=ON`
- `ENABLE_COVERAGE=OFF`

So on a machine without CUDA support, the default script may not be the best entry point. In that case, change the default variable in the CMakeLists.txt file or use a manual CPU-only configuration.

Use this only on systems with a working CUDA toolchain.

```bash
cmake --build . -j "$(nproc)"
```

## CMake Options

The build is intentionally configurable. The main options exposed by `CMakeLists.txt` are:

| Option            | Default | Meaning                                           |
| ----------------- | ------: | ------------------------------------------------- |
| `ENABLE_LOGGING`  |    `ON` | Enables `spdlog`-based logging                    |
| `ENABLE_TESTS`    |   `OFF` | Builds and registers Google Test targets          |
| `ENABLE_DEBUG`    |   `OFF` | Uses debug-oriented compiler flags                |
| `ENABLE_CUDA`     |    `ON` | Enables CUDA language support and GPU targets     |
| `ENABLE_COVERAGE` |   `OFF` | Enables coverage instrumentation for test targets |

### Option details

#### `ENABLE_LOGGING`

When enabled:

- runtime logs are written to `logs/`
- debug and info/error statements become active
- console sink is enabled in debug builds

When disabled, logging macros compile to no-ops.

#### `ENABLE_TESTS`

When enabled:

- Google Test is found or fetched automatically
- CPU and I/O tests are built
- GPU tests are built if CUDA is also enabled

#### `ENABLE_DEBUG`

When enabled:

- C++ uses `-O0 -g`
- CUDA uses `-O0 -g -G`

This is convenient during development and debugging. For performance evaluation, a release build is more appropriate.

#### `ENABLE_CUDA`

When enabled:

- CMake adds CUDA as a project language
- GPU executable and GPU tests are compiled
- CUDA runtime and NPP libraries are linked

When disabled:

- the project still builds the CPU path
- CUDA-specific targets are omitted

#### `ENABLE_COVERAGE`

When enabled:

- test targets are built with coverage flags
- a custom `coverage` target is made available

The CMake file enforces that coverage cannot be enabled without tests.

### Example configurations

#### Minimal CPU-only build

```bash
cmake -DENABLE_CUDA=OFF -DENABLE_TESTS=OFF -DENABLE_LOGGING=OFF ..
```

#### Development build with tests

```bash
cmake -DENABLE_CUDA=OFF -DENABLE_TESTS=ON -DENABLE_DEBUG=ON ..
```

#### Full CUDA development build

```bash
cmake -DENABLE_CUDA=ON -DENABLE_TESTS=ON -DENABLE_LOGGING=ON -DENABLE_DEBUG=ON ..
```

#### Coverage-oriented CPU build

```bash
cmake -DENABLE_CUDA=OFF -DENABLE_TESTS=ON -DENABLE_COVERAGE=ON ..
```

## Usage

The application is command-line driven. Both the CPU and GPU executables use the same argument parser.

## Command-Line Arguments

```text
-i <input_path>     Input directory containing images
-o <output_path>    Output directory for filtered images
-f <filter>         Filter name: grayscale | sepia | brightness
-d <delta>          Brightness delta as a float, only meaningful for brightness
```

### Default values

If arguments are omitted, the parser uses:

- input path: `images/input`
- output path: `images/output`
- filter: `grayscale`
- delta: `0.0`

### Behavior notes

> [!WARNING]
>
> - invalid filters cause the program to print an error and exit
> - unknown arguments also cause an immediate error
> - unsupported file extensions are skipped
> - output directories are created automatically if needed

## Inputs and Produced Outputs

### Expected input

The loader scans a directory and attempts to read supported image files. The repository is documented and tested primarily with:

- `.png`
- `.jpg`
- `.jpeg`

Unsupported files are skipped. For example, the sample `warning.txt` file in `images/input` is ignored.

### Output naming

The output filename is derived from the original filename plus a suffix:

- `Lena.png` → `Lena_grayscale.png`
- `Lena.png` → `Lena_sepia.png`
- `Lena.png` → `Lena_brightness.png`

The exact suffix depends on the selected filter.

### Output directory structure

If you run multiple commands with different `-o` values, you typically get a structure such as:

```text
images/output/
├── grayscale/
├── sepia/
├── brightness_plus/
└── brightness_minus/
```

### Important implementation note about output encoding

At the moment, `save_image()` always uses `stbi_write_png(...)` internally. That means the project writes PNG-encoded output data regardless of the original input format. For PNG inputs, this is naturally consistent. For JPEG inputs, the current filename may preserve the original extension even though the encoder used is PNG.

If you want fully extension-consistent output behavior in a future revision, the save path can be extended to dispatch to a format-specific writer based on the target extension.

## Using Your Own Images

Using your own images is simple:

1. create a folder, for example `images/my_dataset`
2. copy your images into that folder
3. invoke the executable with `-i images/my_dataset`

Example:

```bash
mkdir -p images/my_dataset
cp /path/to/your/images/* images/my_dataset/
./bin/instagram_filters -i images/my_dataset -o images/output/my_dataset_gray -f grayscale
```

For the smoothest workflow, prefer PNG or JPEG-family inputs.

### Important note about the download script and default inputs

The download script saves datasets into `images/random/` or `images/flowers/`, not into `images/input/`. Therefore, after downloading a dataset, either:

- pass it directly with `-i`, or

## Current Notes and Limitations

This section is included intentionally so that the README reflects the current workspace faithfully.

1. **`install.sh` is Linux-oriented**
   - The script uses `nproc`.
   - On macOS, use the manual build flow or replace `nproc` with `sysctl -n hw.ncpu`.

2. **Output writer currently uses PNG encoding**
   - The save path uses `stbi_write_png(...)`.
   - This is important if you process JPEG inputs and expect JPEG-encoded outputs.

3. **Recommended tested image formats**
   - The documented and tested workflow is centered on PNG, JPG, and JPEG images.
   - Unsupported files are skipped automatically.

4. **Configuration header**
   - `include/config.h` is generated from `include/config.h.in` during configuration.
   - If you change project-root-related settings, prefer adjusting the template or the CMake configuration path rather than editing generated files manually.
